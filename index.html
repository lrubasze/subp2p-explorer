How many light peers can a full node actually hold?

The default for --in-peers-light is 100. Measured against a Kusama full node on reference-class hardware, the node holds 3500 with no effect on block import and first loses ground somewhere between 3500 and 4250.

Primary result · 17 runs · 300 s each

The threshold sits between 3500 and 4250 peers

Each point is one run. During a run the node imports a stretch of blocks, and their on-chain timestamps say how much chain time that stretch covers. Chain drift is wall-clock elapsed minus that chain time: a node keeping pace imports 300 s worth of blocks in 300 s (drift ≈ 0); a drift of +12 s means it ended the run 12 s further behind the chain head than it started; negative means it caught up. There is no overlap between the two groups.

Resolution is one block (~6 s) over a 300 s window, since Kusama block timestamps are 6 s apart. The gap between the groups is 2.2 blocks — comfortably wider than that floor. The 5000-peer stall is clamped to the top of the axis at its true value of +138.4 s, so the other sixteen runs stay readable.
What it costs — and what never moved

Holding peers is cheap

Two separate measures, two separate charts. Going from the current default of 100 to 2000 costs roughly +535 MB and +30% of one core. Everything else stayed flat at every count: 0 peers refused, 0 evicted (up to 5000 — the gate is an arbitrary constant, not a capacity limit), 100% announcement coverage, finalization tracking import within 5 blocks, and at most 6220 file descriptors against a 131k limit.

It holds over long runs, and under heavy serving load

The 300 s runs answer where the threshold is. These answer whether 2000 stays safe over time — and whether it survives a node that is also busy serving light-client requests. The serving mix is that request load: while holding the peers, the node also answers runtime-call proofs at 2000/s and runtime-code reads at 345/s (both /light/2) plus warp-sync proofs at 13/s (/sync/warp) — each about half of what it can serve solo. Every sample stays within two blocks of zero and 94% within one — the sawtooth is that quantisation, not the node moving.

Serving load does not move the limit

Six loaded runs alternating with six unloaded baselines, at 2000 peers. The serving mix (calls 2000/s, reads 345/s, warp 13/s — as above) drives the node to 5× the CPU — and the loaded mean drift comes out lower than the baseline mean.

Both columns land on 0 or ±6 s because the metric is quantised to one block — that pattern is the floor, not a signal.

Method, and what the numbers do not cover

How degradation is measured

For the blocks a node imported during a run, compare wall-clock elapsed against the on-chain time those blocks span, taken from the Timestamp inherent: drift = wall_elapsed − chain_time_spanned. No anchor, no assumed block time.

An earlier version of this analysis extrapolated the expected height from a fixed 6.0 s block time. Kusama does not hold 6.0 s — measured windows ran 6.00 to 6.80 — and that method charged the chain's own variation to the node, scoring a 500-peer run worse than a 5000-peer run.

Limitations

  • One machine, one chain, one backend. Kusama, litep2p. The libp2p backend is untested.
  • RAM was 4× the reference spec (125 GB vs 32 GB), most of it page cache for a 1.2 TB database. Block import reads state, so a 32 GB machine could threshold lower. This is the least transferable part of the result.
  • Bandwidth was 2× the reference spec. Irrelevant to peer holding (~250 kB/s at 5000 peers), relevant to serving throughput.
  • Holders are silent and never churn. Serving load was tested separately; connection turnover was not.
  • Single runs at 100, 200 and 500; the counts near the threshold have 2–4 each.
Measured against polkadot 1.24.0-0e181250542, litep2p backend, Kusama, on an AMD EPYC 7232P (8 physical cores, 3.1 GHz) with 125 GB RAM and a 1 Gbit/s link — the reference spec asks for 8 cores @ 3.4 GHz, 32 GB and 500 Mbit/s. Load generated by subp2p-explorer's hold-peers.
