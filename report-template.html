How many light peers a full node carries before it loses the chain

Every peer count up to 5000 was admitted without a single refusal, so the --in-peers-light gate itself is not the constraint. What breaks first is the node's ability to keep up with Kusama's head — and it starts breaking between 3500 and 4250 held light peers.

The threshold: how far the node fell behind during each run

Each dot is one 300-second run. The value is how much the node's distance behind the chain tip grew over the run, so zero means it kept pace and positive means it lost ground. Kusama itself produced blocks at exactly 6.0 s throughout, verified from on-chain authorship timestamps, so this is the node and not the network.

What actually saturates: one async task, not the machine

The bottleneck is libp2p-node, the litep2p event loop. It is a single async task, so it cannot exceed 100% however many cores are idle. The host has 16 cores and the whole process never used more than about one of them; no individual thread went past 11%, because the task migrates across workers and hides from per-thread CPU tools.

The stall, as it happened

Chain drift over the course of four representative runs, each starting from zero. At 2000 and 3500 the traces stay flat. The two 5000-peer runs both climb; one of them simply stops importing for the last 130 seconds.

Announcement spread

Time from the first holder to the last to receive the same block. Linear in peer count up to 2000, then flattening — though at the high end our own 5000-swarm client adds scheduling delay, so treat the tail as approximate.

Node memory

Peak resident set during each run. The slope works out to roughly 0.3 MB per held peer — memory is never the binding constraint on a 125 GB host.
