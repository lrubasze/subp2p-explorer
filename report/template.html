How many light peers can a full node actually hold?

The default for --in-peers-light is 100. We measured a real Kusama full node on hardware close to the reference spec: it holds 3500 light peers with no effect on block import, and starts falling behind somewhere between 3500 and 4250.

2000
is the recommended new default
~2× margin below the measured threshold · 20× the current value
Primary result · 17 runs · 300 s each

The threshold sits between 3500 and 4250 peers

The test: connect N light peers to the node and keep them connected for 300 seconds while the node follows Kusama. The peers do nothing — they only hold their slots. We read the node's own metrics every 5 seconds. One run per data point, N from 100 to 5000, with repeats at the interesting counts. The node's limit (--in-peers-light) was set to 5000 in every run, so what varies is N — the number of peers the node actually holds. We watch three things: does the node keep up with the chain (chain drift), and what does holding cost (CPU, memory).

Chain drift: how many seconds the node fell behind the chain during the run. Two clocks are compared — how much real time passed, and how much chain time the imported blocks cover (from their on-chain timestamps). 0 = kept up; +12 s = ended the run 12 s further behind than it started; negative = caught up. Each point is one run. The metric only resolves whole blocks (~6 s), and the gap between the two groups is 2.2 blocks — clearly wider than that. The 5000-peer stall (+138.4 s) is drawn at the top edge so the other sixteen runs stay readable.

Connection memory

How much the node's memory jumps while the peers connect (run start → t=120 s, MB). This isolates the cost of the connections themselves — the node's memory also grows slowly on its own, and runs were not separated by restarts. Below ~1000 peers the jump is smaller than normal 2-minute noise, so the left-most points mean little.

Reading the three charts

  • Chain drift: flat up to 3500 peers (−13.0…+1.4 s). Every run at 4250 or more falls behind (+7.1…+138.4 s). No overlap — the limit is somewhere between 3500 and 4250 held peers.
  • CPU: 46% of one core at 100 peers, ~105% at 5000. Cheap — CPU is not what fails first.
  • Memory: ~45–70 KB per held peer, measured as the jump while the peers connect — about +115 MB for going from 100 to 2000. (Comparing whole runs instead gives a ~4–5× higher number, because the node's memory also grows slowly with uptime — see the memory chart in the next section.)
  • The limit itself never does anything: 0 peers refused, 0 evicted, every announcement delivered, at every count. The node accepts every peer offered; what breaks first is keeping up with the chain.
  • Candidate: 2000 — flat in all four runs, about half the threshold. The long-term test below runs at this count.
Long-term test · the candidate default

2000 peers, held for hours

Three long runs put the candidate through time, alone and while the node is also busy serving light clients:

  • 6 h · peers only — 2000 held peers, no request load
  • 6 h · peers + serving mix — the same 2000 peers while the node also serves requests
  • 12 h · peers + serving mix — the same, for twice as long

The serving mix, each part at about half of what the node can serve at most:

  • runtime-call proofs at 2000/s (/light/2)
  • runtime-code (:code) read proofs at 345/s (/light/2)
  • warp-sync proofs at 13/s (/sync/warp)

In the chart below, every sample stays within two blocks of zero, and 96% within one. The zig-zag is the one-block resolution of the metric — not the node speeding up and slowing down.

Memory over the long runs

growth in resident memory since run start (ΔRSS, MB)
Shown as growth since each run's start, because the absolute levels can't be compared: the node was never restarted between runs, and the serving runs leave memory behind even after the load stops. Secondary check · serving load

Serving load does not move the limit

Six runs with the serving mix on, alternating with six without it, all at 2000 peers. The mix (calls 2000/s, reads 345/s, warp 13/s — as above) pushes the node to 5× the CPU — and the loaded runs' average drift comes out lower than the baseline's.

Every value lands on 0 or ±6 s because the metric resolves whole blocks — that pattern is the resolution, not a signal.
For the record

Every run

What the columns mean:

  • peers / held — peers offered to the node, and how many it actually held (peak)
  • drift — seconds the node fell behind the chain during the run (red = fell behind)
  • blocks / window — blocks imported during the run, and the run length
  • coverage — share of block announcements that reached every peer
  • spread p50/p99/max — for one block, the time between the first and the last peer getting its announcement; p50 is the middle block, p99/max the slowest
  • refused / evicted — peers the node turned away, or dropped after connecting
  • finality lag — how many blocks finalization ran behind best
  • fds peak — open file descriptors of the node process, mostly one TCP socket per peer (limit 131,072)
  • ramp ΔRSS — memory jump while the peers connect: the per-peer cost
  • RSS peak / CPU — highest memory and average CPU during the run

Method, and what the numbers do not cover

How degradation is measured

Two clocks are compared: real time passed during the run, and chain time covered by the blocks the node imported (read from each block's own timestamp): drift = wall_elapsed − chain_time_spanned. Nothing is assumed about how fast the chain makes blocks.

An earlier version assumed Kusama makes a block exactly every 6.0 s. It does not (measured 6.00–6.80 s), and the wrong assumption produced more fake "lag" than the real signal — it scored a 500-peer run worse than a 5000-peer run. Always compare against real block timestamps.

Limitations

  • One machine, one chain, one backend. Kusama, litep2p. The libp2p backend is untested.
  • Our machine has 4× the reference RAM (125 vs 32 GB), and most of it caches the 1.2 TB database. Importing blocks reads that data, so a 32 GB machine could fall behind at a lower peer count. This is the weakest part of the result.
  • The network link is 2× the reference. Doesn't matter for holding peers (~250 kB/s at 5000 peers); matters for serving throughput.
  • Our peers are silent and never disconnect. Serving load was tested separately; peers coming and going was not.
  • Single runs at 100, 200 and 500; the counts near the threshold have 2–4 each.
Measured against polkadot 1.24.0-0e181250542, litep2p backend, Kusama, on an AMD EPYC 7232P (8 physical cores, 3.1 GHz) with 125 GB RAM and a 1 Gbit/s link — the reference spec asks for 8 cores @ 3.4 GHz, 32 GB and 500 Mbit/s. Load generated by subp2p-explorer's hold-peers.
